# Chapter 4 data availability

This describes what the dashboard currently records. It does not change the research proposal or infer missing observations.

| Planned metric | Logged fields that help compute it | Still manual or missing |
|---|---|---|
| Packet delivery | Unique uplink sequence, reception timestamp, heard-by node, direct/checkpoint path, duplicate marker, relay RSSI/SNR and hop-delay field | Sent-packet denominator and a reliable originating send timestamp are not available from the base-side ingest alone. Do not treat received rows as a delivery ratio. |
| Command latency | Command creation, first bridge fetch and reported-sent timestamps; derived elapsed milliseconds; direct/relay route | Hiker receive-side timestamp and timer outcome are firmware/record-sheet data. Logged elapsed time ends at the bridge's sent report. |
| Position error | Stored reported latitude/longitude, GPS accuracy, satellite count; valid-fix display/export derivation. Phase 2 gate checks (migration 015): the mean position of two 10 s windows (inside and outside marker), phone distance between them, and the signed error against the typed tape distance; mean signed, mean absolute and largest absolute error are shown as separate labelled lines; CSV `type=position_errors`. | The tape or measuring wheel distance at each gate is measured and typed by the operator. The optional absolute error at a known point (2 min average) is not built. The pause average is computed by the dashboard from packets in an operator-stamped window, not logged by the app. GPS accuracy field is device-reported, not measured error. |
| Gate marker acceptance (Phase 2) | Marker checks (migration 014): mean of valid fixes in an operator-chosen window, its classification against the stored polygon, the intended class, a match flag, warnings for short windows or few fixes; CSV `type=marker_checks`. | Which marker is intended inside or outside, and moving a marker that failed, are operator decisions. A check with no active polygon is saved as UNCLASSIFIED. |
| Phase 1 classification match | Operator annotations (migration 012): intended INSIDE/OUTSIDE, point source (from the track or moved beyond the margin), and whether the stored classification matched, in the packet log and packet CSV. | The intended class is entered by the operator; nothing is added to the uplink. Replay outside points cover the outer side only. |
| Crossings, miss rates and return to safe (Phase 2/3) | Crossing records (migration 013): reference packet, valid-fix fields, outside count, inside/outside flips, reports after re-entry, return-to-safe time, candidate-only false-alert count; CSV `type=crossings`. All computed from packet `received_at`, which has one-second precision. | Alert latency, alarm screen, noticed and understood fields, and remarks are entered by hand. The 15 s crossing-level and 2 s packet-level outcomes are not inferred. |
| Alert time | Uplink receive time, event create time, command create/fetch/sent time, event type | Phone warning display/receipt timestamp and the hiker's 2 s/15 s timer observations come from record sheets / firmware. The backend does not infer pass/fail. |
| Battery life | Reported battery level per uplink and event timestamps | Start/end phone battery readings, screen/app conditions, and sampling schedule must be recorded manually. No continuous battery telemetry is invented. |
| Wrong-node receptions | Heard-by node and reception path are logged | Intended destination vs. actual receiving node and wrong-node outcome need record-sheet/firmware observations. The dashboard does not infer wrong-node delivery. |

Rows flagged DEMO, REHEARSAL, or TEST are excluded from research summary counts; CSV exports retain rows and label their source.

Times in API responses and CSV exports are naive UTC strings (the database session and PHP run in UTC). Rows written before the UTC change can mix clocks, and packet `received_at` has one-second precision.
